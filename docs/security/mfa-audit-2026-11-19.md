# Two-factor authentication audit — 2026-11-19

## Findings

- **Enrollment activation:** `startEnrollment` creates an encrypted, unenrolled secret. `confirmEnrollment` checks a six-digit TOTP and atomically marks the factor enrolled and issues ten single-use recovery codes. Invalid or replayed steps do not enroll.
- **Secret handling:** The server generates 20 random bytes with `crypto.randomBytes`, Base32 encodes them, and encrypts the secret before database storage. The enrollment endpoint requires an authenticated session or a short-lived admin enrollment token. It returns the secret and `otpauth://` URI only during setup. The API sends `Cache-Control: no-store`; the UI keeps the payload in component state, never in a URL or browser storage. The QR code is generated in the browser, with no external QR service. Route logging records failure category and route rather than request bodies. No analytics call in the setup component receives the secret.
- **Login and recovery:** Enrolled users receive a login challenge instead of a session. A successful TOTP or unused recovery code is required to create a verified session. Recovery codes are salted and hashed, consumed once, and replaced on regeneration. Password reset revokes sessions and requires a fresh login; it does not remove MFA. Disable requires the password plus a TOTP or recovery code, and revokes other sessions. Admins cannot disable mandatory MFA.
- **Rate and replay controls:** The login challenge has a ten-minute lifetime; code endpoints have account-based and IP-based limits. Accepted TOTP time steps are recorded and rejected on reuse, including across challenges. Confirmation, regeneration, and disable also use this step guard.
- **Confirmed session gap, fixed here:** Before this change, a regular user's password-only session created before enrollment remained usable afterward, including refresh. Enrollment confirmation now upgrades the confirming session and revokes all other sessions in the same transaction. Access and refresh checks already reject revoked sessions. The new disposable-database test exercises both old and confirming sessions.

## Setup UX

The previous settings screen printed the manual secret and full enrollment URI with no QR code. The new screen renders a local QR code, offers a secondary manual-key disclosure, requires a six-digit confirmation, and lets the user cancel the in-memory setup view. The server's pending unenrolled row remains harmless if setup is abandoned; a later start replaces it. Recovery codes remain visible only until the user dismisses them.

## Scope and remaining risks

This is a source and local-test audit, not a penetration test of deployed infrastructure. The audit did not inspect hosted database contents or runtime observability configuration. Browser extensions, device compromise, and screenshots can capture setup material visible to the account holder. Users who lose both authenticator and recovery codes have no self-service MFA bypass; recovery requires an established support process. No schema migration or hosted data change is included.
