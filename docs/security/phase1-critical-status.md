Capture role names and booleans only, never connection URLs or secret values.

**Preview role cutover:** first resolve the recorded `licensed_chapter_cache_id_seq` USAGE gap on the Preview runtime role. Recheck all expected table, schema, sequence and RLS privileges in an isolated clone. Approve and apply only the minimum missing grants. Put the replacement role credential in Preview scope only; change Preview app connection setting; restart Preview; verify connection identity, login, notes/bookmarks/highlights/reading state, cache miss, RLS isolation and zero 42501 errors. Revoke old role login/credential only after smoke tests pass. Expected impact: brief Preview reconnect and possible transient failures. Roll back the Preview connection setting to the known-good prior value if smoke fails, then investigate before retrying; retain audit evidence. A rollback temporarily restores the known High exposure, so use a short window and contain access.

**Credential retirement:** inventory migration-era owner/runtime credentials and local connection files without copying values into reports. After approved rotation, update only the intended environment scope, test new connections, verify old credentials fail, remove saved URLs from managed local files and secret stores, and document revocation time. Roll back by issuing a new restricted credential and restoring the prior service configuration from a protected record; do not re-enable a known leaked credential.

**Three-project privilege and environment isolation:** produce a matrix of App/Bible/Commentary × Preview/Production × owner/migration/runtime/backup role. Verify runtime roles lack administrative attributes and unnecessary write grants; backup roles are read-only; Preview variables point only at Preview project/branch identities. Any revoke or scope change needs its own impact check, approved statement set, and rollback grant set. Prove isolation via non-sensitive `current_database`, `current_user`, and project/branch identity evidence, without querying user rows or testing live cross-environment writes.

**Deployed HTTP attestation:** on the exact deployed commit, use synthetic accounts and harmless requests to capture allowed/denied CORS preflights, CSRF header/Origin rejection, JSON 400/404/413, cookie flags, HTTPS redirect and HSTS. Record status and header names/values only; redact tokens and cookies. These checks are read-only except synthetic-account lifecycle and must not touch real user data.
