# Scroll-driven laptop prototype

This prototype is isolated on `prototype/gnosis-laptop-scroll`, based on PR #28. It does not update that PR or production.

## Run and integrate

From `frontend`, run `npm ci`, `npm test`, `npm run build:check`, and `npm run dev`. Open `/`. Integration consists of the `LaptopScene` import and component inside the existing `.landing-hero-media`, after its original `<picture>`. The existing picture remains the accessible static fallback. No hero wording, navigation, typography, routes or other sections change.

`LaptopScene.jsx` owns preference detection, loading, scroll/resize events and cleanup. `mountLaptopScene.js` owns Three.js rendering and GPU resources. `createLaptopModel.js` contains the entire original procedural model: fixed keyboard/base and independently hinged front/back/edge geometry. `laptopMath.js` contains scroll mapping and projective screen texture mapping.

Scroll progress across the first 55% of the hero height maps directly from 110 degrees open to zero degrees closed. Scrolling upward reverses that mapping; no autoplay, sticky scroll trap, parallax or frame crossfade is used. The base and camera never animate. The landscape and phone are one fixed image; only the lid and its real-time shadow change. Normal page scrolling still moves the hero through the viewport.

The screen texture samples the existing approved `hero-1672.jpg` screen corners through a homography. The scene uses a single perspective camera, warm directional illumination, environment lighting, contact shadow and dynamic lid shadow. No external device model or device branding is introduced.

## Performance and fallback

Three.js 0.187.0 is exact-pinned in the lockfile (npm registry integrity included); no GSAP dependency is needed for a direct scroll-to-angle mapping. Three.js uses the MIT license. Its approximately 138 kB gzip renderer chunk is lazy-loaded only on fine-pointer desktops at least 1100 CSS pixels wide, without reduced motion. Other sizes, coarse pointers, reduced motion, unavailable WebGL, and asset failures retain the original hero photograph.

Rendering runs on demand, coalesced into requestAnimationFrame, with DPR capped at 1.5. It pauses while hidden/offscreen rather than using a continuous animation loop. Unmount/preference changes abort initialization, remove listeners, cancel frames and dispose GPU resources. A preference change restores the original photograph. The image dimensions/aspect ratio reserve layout space.

The lazy Three.js chunk exceeds Vite's default 500 kB minified warning threshold. The warning is retained. This is a prototype, not a claim of photographic equivalence: the procedural metal model, lighting and shadows can be further art-directed before production. Low-powered desktop performance and hardware/browser variations still require real-device review.

- `frontend/public/images/landing/laptop-prototype/desert-clean-plate.jpg`: optimized delivery plate, generated from the PNG using macOS sips JPEG quality 88.
- All laptop geometry, keyboard legends, contact shadow and materials are generated by the included source code; no downloaded 3D model license is required.
- The user's ZIP was inspected as reference only. Its six-frame conceptual crossfade and drifting landscape/device images are not used in the implementation.

The clean plate was created with the built-in image-generation tool, using the approved original desert hero as an edit reference. Prompt: remove ONLY the complete laptop on the right including its shadow; preserve the phone, sunset dunes, vegetation and framing; leave photoreal clean sand; no laptop parts, added text, restyling, zoom or moved phone. Image generation produces small background differences; this is not a pixel-identical restoration. The original files and static fallback are retained.

## Verification

Automated tests cover open/closed/reversed/clamped progress, all four projective screen corners, stationary base and hinge with actual Three.js geometry, mobile/reduced-motion fallback, Strict Mode cleanup, late asynchronous initialization after unmount, preference changes and renderer failure. Browser checks use the actual WebGL renderer and record opening angles while scrolling down and up. Compare open/half/closed screenshots, verify the existing navigation and calls to action, and check mobile and reduced-motion fallback before production consideration.

No backend, database, authentication, environment or deployment configuration changes are required. Deploy this branch only to a preview environment for review; do not promote or merge without approval.
