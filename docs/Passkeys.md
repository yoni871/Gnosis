# Passkeys

Passkeys are an optional sign-in method. Password sign-in and the existing MFA recovery-code flow remain available. Registration and removal require a valid session and the current password; the password verifier accepts both existing bcrypt hashes and current Argon2id hashes. Password confirmation is limited to five attempts per account in 15 minutes, including attempts from different IPs.

A login assertion must verify the relying-party ID, exact frontend origin, challenge, signature, and authenticator user verification (PIN, biometric, or equivalent). Registration requires a discoverable credential; login options carry no credential IDs and use the same response shape for known and unknown accounts. Unknown accounts receive an unpersisted challenge. Challenges expire after ten minutes and are consumed once, before assertion verification. A signed assertion without user verification cannot satisfy MFA. A successful assertion writes its credential counter and session in one transaction. Counter regression flags the credential and denies login.

The session transaction locks the user, requires a verified email, and reads the current `user_mfa` row. It refuses an unenrolled admin. An enrolled account gets `mfa_verified=true` and the current `mfa_generation`; an unenrolled account gets `mfa_verified=false` and no generation. This follows the session assurance model on `main`.

The passkey migration belongs to the App database. The runtime role needs schema usage, `SELECT, INSERT, DELETE` on `user_passkeys` and `webauthn_challenges`, plus column-level `UPDATE` on passkey `counter`, `last_used_at`, `flagged_at`, `label` and challenge `used_at`. It needs no migration or table ownership privileges. The disposable database harness tests these grants. Actual hosted role grants were not queried; operators must verify them before deployment. No hosted migration was run.

Pending PR #95 adds RLS policies for notes, bookmarks, highlights, and reading state. It does not cover passkey tables. Passkey queries use explicit `user_id` predicates for account-scoped management. Login looks up a credential globally by its ID after matching it to a stored challenge's user ID. Adding RLS to passkey tables later requires a separate design for unauthenticated login and the same runtime-role audit as PR #95. The two PRs also add ordered App migration catalog snapshots from different branches; whichever merges second must reconcile its later snapshot and rerun migration checks. This PR does not change #95.
