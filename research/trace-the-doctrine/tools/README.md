# Trace the Doctrine — Validation Tools

Structural checks for the research data in `research/trace-the-doctrine/`.
These tools check structure only: that references resolve, dates are
consistent, quotations carry a usable source location, and publication
state matches verification state. They do not judge whether a quotation
is accurate, a date is right, or a claim is true -- that is the work of
Phase 4 verification and independent QA (see `RESEARCH-STANDARDS.md`
§8-9).

## Running the validator

From the repo root:

```sh
python3 research/trace-the-doctrine/tools/validate.py
```

Exit 0 with an OK summary when clean; exit 1 with an error list on any
failure. Standard library only, no network access. `--root DIR` validates
a different copy of the research tree (used by the tests).

## What it checks

1. **Scripture boundaries** -- every passage's book, chapter, and verse
   range exists in the 66-book Protestant canon (`canon.json`, KJV verse
   numbering; per-book totals checked against the published KJV chart).
   `canonicalOrder` must match the book's canonical position.
2. **References** -- every interpretation's `passageId`, `authorId`, and
   `workId` exists; every passage cross-reference, milestone passage
   link, milestone author link, work author link, and alternative-reading
   author/work link resolves.
3. **Verification records** -- every `verificationRecordIds` entry names
   a record that exists; every record is cited somewhere or is covered
   by a rule in `uncited-records.json`; every record's `claimId`
   resolves to an entity id, or starts with `<passage-id>-` for a claim
   about a passage (e.g. `heb-1-3-ref`).
4. **Quotations** -- a non-null quotation must have a location that is
   present and well-formed (a number, a Roman numeral such as
   "Chapter II", or a locator word such as chapter/section/letter); a
   reproducible quotation must carry its text; a non-reproducible one
   must carry a summary; a citation, when present, must contain an
   http(s) URL.
5. **No missing or duplicated records** -- ids are unique within each
   collection, and every passage, interpretation, and milestone has a
   `<id>.md` note file (no orphans, either direction).
6. **Chronology** -- in every date object, earliest <= latest; a `range`
   needs both endpoints, an `exact` date needs its year; milestones are
   in non-decreasing earliest-date order.
7. **Schemas** -- every JSON data file validates against its Phase 1
   schema (`schemas/*.schema.json`). The blank
   `trinity/verification-record.template.json` is not a record: only its
   keys are checked against the record schema's properties.
8. **Publication / approval** -- an entity with status `verified`,
   `editorially-approved`, or `published` may only cite records whose
   result is `verified`; an `editorially-approved` or `published`
   entity additionally requires editorial approval on every cited
   record; a record with editorial approval must have result
   `verified`.

## Files

- `validate.py` -- the validator (stdlib-only Python 3).
- `canon.json` -- per-chapter KJV verse counts for all 66 books, with
  per-book totals. Generated by the script that built it; if the canon
  ever needs correcting, fix the generator and re-verify every book's
  total before regenerating.
- `uncited-records.json` -- rules (id prefix + reason) for records that
  are legitimately cited nowhere. The current rule covers the `ver-p4-*`
  Phase 4 second-pass records: entities list their Phase 2/3 records by
  design, and the Phase 4 records are accounted for in
  `trinity/verification-phase-4-summary.md`. Add a rule here -- with the
  reason -- when a new class of legitimately uncited records is
  introduced; never add one to hide a missing citation. A rule that
  matches no records is harmless -- a young doctrine tree may
  legitimately have no Phase 4 records yet.
- `tests/test_validate.py` -- fixture tests (stdlib `unittest`). Run
  with `python3 -m unittest discover -s tests -v` from this folder.

## When the validator fails

Fix the data, not the validator. If a check itself is wrong -- a rule
that misreads the standards -- flag it to the EM instead of weakening
the check in the same change that needs it to pass.
